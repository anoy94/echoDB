# 低置信度二次建议：复核结论与 MVP 补充

复核日期：2026-11-06。对照文件：同目录下的《低置信度二次建议.md》《RAG测评设计_技术评审与改进建议.md》及研究来源旁证。

## 结论

这份建议最有价值的是提醒收敛实现范围。文本证据先采用固定原文摘录、首版只开放有限的上下文替换、分层补标替代证据，均可以采用。但它将“简化工程”与“简化判定逻辑”混在了一起：前者合理，后者有一处严重失真。

不能采纳“Oracle 答对就 100% 证明检索/重排漏召回”，也没有依据支持“解决 90% 归因争议”“80% 时间用于字符对齐”“成本指数级增长”等数字和增长断言。

| 二次建议 | 复核判断 | 推荐落地 |
|---|---|---|
| 文本先用原文摘录/指纹，不强制全局 offset | 有条件采纳；确实能减少首版定位工作，但 hash 不负责模糊匹配 | 固定文档版本 + quote + 限定范围 + 消歧信息；char_span 可选 |
| 只做 Oracle Context Bypass | 采纳缩小能力范围；否定其确定性归因结论 | 一个明确的 generate_with_context 接口，报告“上下文替换后恢复”，不直接宣判根因 |
| 等价/替代证据先覆盖核心集 | 采纳；自动扩展集不必穷举 | 标注完备性显式记录；未知替代证据进入复核 |
| PPI 推迟 P2 | 采纳，但上一版已经这样安排 | 先人工校准、配对差异与不确定性；PPI 按需求引入 |

这些建议主要改进“实施边界”，没有推翻稳定证据、指标可测性、独立校准和受控实验的设计原则。

## 1. 文本锚点：采纳轻量方案，保留稳定参考

### 1.1 它指出的困难真实存在，但对上一版有部分误读

上一版要求的是固定 canonical 参考中的 span，不是要求所有 parser 输出都共享相同 offset。只要参考文本版本冻结，参考侧 offset 本身不会随待测 parser 改变；难点在于将不同输出映射到该参考。

不过，上一版把 char_span 放在主要示例里，容易让开发者误以为必须先实现跨格式、全局字符级对齐。这一点应明确放宽：**第一版保证证据身份稳定即可，精确字符位置可以后补。**

这里的“稳定摘录”也不是由每个 parser 分别生成的段落，而是从冻结原文中独立核验的一段参考文本。

### 1.2 推荐的最小文本 locator

```json
{
  "evidence_id": "E_PLAN_001",
  "document_id": "plan_report",
  "document_revision": "source_revision_A",
  "locator": {
    "kind": "text_quote",
    "scope": {"section_path": ["2024年", "第三季度", "云业务"]},
    "quote": "第三季度云业务营收计划为1亿元。",
    "prefix": "季度经营计划",
    "suffix": "执行情况将在季末披露。",
    "normalization_version": "text_normalizer_v1"
  },
  "verification_status": "source_verified"
}
```

这是数据结构示例，文本和 ID 为占位。已有可靠页码或结构节点 ID 时加入 scope；它们不是所有格式必须具备的字段。另存 canonical revision/char_span 也可以，但不作为首版硬前提。

匹配可按以下顺序实现：

1. 限定相同 document_revision，在可用的页/章节/节点范围内匹配。
2. 先精确匹配，再使用固定版本的保守归一化，例如统一空白。
3. 有必要时用模糊检索产生候选；对金额、年份、单位、否定词、比较符等另行核验。
4. 多处相同摘录用 prefix/suffix 和位置消歧；不能唯一判定则返回 ambiguous。
5. 将匹配结果、位置、方法和判定依据缓存到运行映射，不改写 gold。

**hash 用于身份校验、去重和缓存，不能直接处理 OCR 错字或模糊定位。** 文本相同也可能在一份文档出现多次，仅靠 hash 无法识别具体出现位置。不要把“2023”和“2024”之类的差异归一化掉。

如果答案依赖两处证据，应分成两个可定位单元；不要为了容易匹配而要求一整个长段落必须出现在同一个 chunk 中。字符串匹配只能证明某段文字出现，不能替代主张支持关系的核验。

### 1.3 “映射失败”与“系统漏检”必须区分

| 观测 | 应怎样解释 |
|---|---|
| 固定源文证据可确认，但 parser 的全量输出丢失该事实 | 解析信息损失，可以计为解析缺陷 |
| 能在 parser/索引全量材料中定位，但最终上下文没有它 | 候选检索、排序或组装链路的证据丢失，需要继续区分阶段 |
| 输出可能包含改写后的事实，匹配器无法可靠判断 | 映射不确定，报告测量覆盖；不能自动算漏召回或算通过 |
| 同一摘录出现多次且无法消歧 | ambiguous，需补充范围或复核 |

降低定位精度的代价是测量能力减少，应公开 coverage/unresolved 数量。不能只保留容易匹配的题，再宣布所有格式召回很好。

### 1.4 表格/图片也不应无条件“完全采纳”

固定 PDF 的页和 bbox 很适用，但 DOCX 页码随字体、排版环境变化；表格行列索引也可能随 parser 错误或合并单元格表示变化。

参考侧的页/行列/框应绑定固定源文或冻结渲染版本。第一版可先覆盖格式最稳定、业务最重要的材料；没有可靠 bbox 的样本先保留文档、图片 asset ID、表头/单元格参考与较粗范围，不伪造精确坐标。

## 2. Oracle 旁路：采用有限接口，保留诚实的结论

### 2.1 不需要先开发通用 DAG 工作流引擎

这一工程收敛建议合理。首版可以只支持：

```text
run(query, history, config)
generate_with_context(query, history, supplied_context, generation_config)
```

也可以导入已有运行记录，再调用第二个接口。执行图可以只是 Trace 的存储表示，不必由框架负责调度整个业务系统，更不需要实现任意热替换、崩溃恢复和持久化工作流。

旁路必须复用原生成阶段的模板、模型配置、会话、输出预算及相关权限/工具规则，只替换可控的上下文。保存实际请求，明确 gold 的组装、排序和长度。

如果接入方无法暴露原生成配置，只能拿另一个 prompt 再问一次，应称为“替代生成实验”，不能视为原系统的严格干预。

### 2.2 “答对就证明漏召回”的反例

假设原上下文已经包含计划 1 亿、实际 1.2 亿，但它们位于很长的噪声材料中；模型首次答错。换成只有这两个事实的 gold context 后，模型答对。

两条证据原本都已召回，变化可能来自：

- 干扰减少或证据位置改变；
- 组装格式、引用布局、截断处理；
- 模型对相同事实的利用能力和生成波动。

因此该结果至多支持：**该次错误在所记录的上下文替换条件下得到恢复，值得排查上下文供应或利用链路。**

即便是严格只改变 context，也只能评估该干预的效果；从“改变整份 context 有效”无法再唯一推导成“检索漏召回”。这些是不同粒度的问题。

### 2.3 推荐判读表

| 正常运行 | Oracle 运行 | 可以报告 | 不能直接断言 |
|---|---|---|---|
| 错 | 对 | 在该干预下恢复；增加上下文链路问题的嫌疑 | 检索/重排必然漏召回；生成器没有问题 |
| 错 | 错 | gold 条件下仍失败；查生成、模板、输入、gold 和题意 | 一定是模型推理能力差 |
| 对 | 错 | 干预存在退化；查 gold 完备性、旁路一致性或波动 | 正常运行必然依靠幻觉 |
| 对 | 对 | 两种条件均成功 | 检索必然必要或全部组件均正确 |

最小报告字段可用：baseline/oracle judgment、config/request IDs、上下文摘要和 token 数、替换范围、试验次数。没有经验证的概率估计时，不输出“根因置信度 100%”。

### 2.4 失败触发可以省成本，但不宜作为唯一抽样规则

优先对失败样本跑 Oracle 合理。为发现失败检测器漏判、gold 错误和干预退化，另取少量通过样本或独立随机样本做检查；比例由预算决定，不必预设固定值。

对准备作为根因证据的重要案例，可重跑正常条件和 Oracle 条件，减少一次生成随机性影响。第一版不必为所有题重复很多次，但应诚实地称单次结果为线索。

如果只对判错样本执行，应报告“在被判错并接受干预的样本中，恢复了多少”，不能外推为全库的根因比例，也不能在没有实验的情况下宣称解决 90% 争议。

### 2.5 上一版的优先级应更明确

“复现一次完整运行”“重新调用生成器”“向任意阶段注入产物”是三个不同能力。首版完成运行记录及按配置重跑；有生成接口时加 Oracle。通用阶段回放和组合干预放后续，不将它们作为基础端到端评测的接入门槛。

## 3. 替代证据：不穷举，仍需管理标注不完备

建议采纳，但需细分两个概念：

- 同一事实的不同来源，是某个证据单元的替代项。
- {E1,E2} 或 {E3,E4} 均足够，是整套充分证据组合的替代；组内 AND、组间 OR。

首版至少允许表达“已知的一组充分证据”，人工核心集中优先补充已发现的有效替代。自动扩展集不要求穷举全库。

可增加 `relevance_annotation_scope: partial | pooled_reviewed | audited_scope`，并记录实际审定的语料/候选范围；不要仅凭一个枚举值宣称全库证据完备。

当待测系统返回不在 gold 列表里的证据：

1. 已人工审定等价：正常计入。
2. 尚未审定：记为 unjudged，进入候选池或按预算复核。
3. 已核验不能支持：才可判不相关/不支持。

允许按当前已标证据算召回，但名称和报告应说明“对已标证据的召回”，不能把漏掉某个锚点解释成没有找到任何有效答案证据。只认最初合成锚点会系统性惩罚新检索器。

低预算下可以把主张支持判断用作辅助，仍需标明这是经校准的 judge 估计，并对分歧抽检。不要悄悄把“精确 gold ID 召回”和“模型估计的语义支持率”混成同一指标。

## 4. PPI 延后：确认原有安排，补清统计边界

上一版第 6 节已建议首版人工校准+配对比较，第 10 节也已将 PPI 放入 P2，因此这里主要是确认优先级。

需要区分：

- **配对实验**：同一用例上比较 A/B；可以使用正确率、成本等客观结果，不一定需要 pairwise judge。
- **Pairwise judge**：直接判 A/B 谁更好，仍可能有位置、文风等偏差，仍需人工校准。
- **Judge 混淆矩阵**：需要独立人工标签。检查漏判和误判，不能只看整体 accuracy。
- **PPI**：借人工标签与自动预测估计总体量和区间；不是修复每条标签的工具。

首版可以延后 PPI，但不能同时延后人工基准、有效样本数、测量覆盖和基本不确定性报告。对于有足够样本的比较，用成熟统计实现给出配对差异区间即可，无需自己开发统计框架。

是否引入 PPI，主要看人工标注成本、总体估计需求及代表性抽样条件；不是等“技术够前沿”就必须引入。

## 5. 建议收敛后的首版范围

| 能力 | 首版保留 | 后续再加 |
|---|---|---|
| 证据定位 | 文档快照、固定 quote、可用范围、匹配状态 | 跨格式全局字符映射、精细区域对齐 |
| 调度与追踪 | 固定流程/现有执行器、实际候选与最终上下文 | 通用流程调度、任意阶段恢复 |
| 干预 | 有接口时做 Oracle；明确不支持状态 | 多阶段组合干预与交互分析 |
| 替代证据 | 已知充分组、核心样本补标、unjudged 候选池 | 全库更广泛的替代证据发现 |
| 裁判 | 人工核心集、规则、judge 校准、错误/不确定状态 | PPI、主动采样和更复杂成本优化 |
| 比较报告 | 同预算、配对、关键切片、区间、失败覆盖 | 大规模自动配置搜索与复杂策略优化 |

不应作为工程降维牺牲的底线：原始语料/数据集/模型/裁判版本，黄金参考独立性，权限与预算约束，错误/不确定状态，裁判基本校准，以及不把故障假设包装成确定根因。

## 6. 依据与文档关系

本次重点是对四条建议的工程与逻辑复核，复用已核实的一手来源，不新增未经查证的百分比或工期估计：

- 主评审第 4.3/9 节：固定参考与运行映射；本补充将 char_span 明确为可选。
- 主评审第 8 节：Oracle 更短、更干净和多故障的局限；本补充给出最小接入和更严格判读。
- 主评审第 6/10 节：PPI 已延后；本补充解释配对实验、pairwise judge 与人工校准的区别。
- [Sufficient Context](https://arxiv.org/abs/2411.06037)：区分证据不足与证据利用失败；不能据此把一次 Oracle 恢复等同于漏召回。
- [ARES 官方实现](https://github.com/stanford-futuredata/ARES)：人工验证与 PPI 的总体估计作用。
- [LangSmith 官方评测概念](https://docs.langchain.com/langsmith/evaluation-concepts)：数据集、实验、trace 与人工回流的基础闭环。

本补充给出的是可实施的取舍建议，未对“能节省多少工时”“能覆盖多少归因争议”作实测保证。
